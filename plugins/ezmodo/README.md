# EzModo plugin for Claude Code

One `/plugin install` gives Claude Code the EzModo MCP tools **and** the working
discipline that makes an agent use them — instead of a manual `claude_desktop_config.json`
edit plus a 700-line `CLAUDE.md` every consuming repo has to copy by hand.

Part of E-252.

## Install

```bash
# In Claude Code
/plugin marketplace add EasyModeOnly/ezmodo-plugins
/plugin install ezmodo@ezmodo
```

To try local changes without publishing, point the marketplace at a checkout.
The path needs a leading `./` or `/` — a bare `.` is rejected as an invalid
source format:

```bash
claude plugin marketplace add ./          # from the repo root
claude plugin install ezmodo@ezmodo
claude plugin details ezmodo@ezmodo       # component inventory
```

Validate both manifests before committing a change to either:

```bash
claude plugin validate --strict plugins/ezmodo   # the plugin manifest
claude plugin validate --strict .                # the marketplace manifest
```

## Where this is published

Customers install from **`EasyModeOnly/ezmodo-plugins`**, a public repo that
contains only this directory and the marketplace manifest. This monorepo stays
private and stays the source of truth; the mirror is generated by
`.github/workflows/public-mirror.yml` on every push to main that touches
`plugins/**`.

That indirection exists because `/plugin marketplace add` resolves a repo with
the **viewer's** credentials. A plugin in a private repo is installable only by
people who already have access to it — which is everyone except the customers
it was built for.

**Never edit the mirror.** A change made there is overwritten by the next sync,
silently. Everything here is what ships.

## Layout

```
plugins/ezmodo/
├── .claude-plugin/plugin.json   # the plugin manifest
├── commands/                    # /ezmodo:start | resume | untracked | submit
├── skills/                      # work-tracking, link-upkeep, db-schema-snapshot
├── hooks/                       # commit linking, untracked-edit drift
└── .mcp.json                    # the EzModo MCP server
```

`commands/`, `skills/` and `hooks/` are the conventional directory names, so
`plugin.json` does not restate them. Listing a path that equals the default adds
a second place the layout is written down and nothing that keeps the two in
agreement.

### Why the plugin lives in a subdirectory

The marketplace manifest (`.claude-plugin/marketplace.json`) has to sit at the
repo root for `/plugin marketplace add EasyModeOnly/ezmodo-plugins` to resolve, but the
plugin itself does not — it is referenced by `source`. Putting the plugin at the
root would claim the top-level names `commands/`, `skills/` and `hooks/` in a
monorepo that already contains `web/`, `api/`, `cli/`, `mcp-server/` and — the
concrete collision — a `hooks/` directory holding the repo's git `pre-commit`
hook. `plugins/<name>/` keeps the plugin self-contained and leaves room for a
second one.

### Paths inside the plugin

Anything in `.mcp.json` or `hooks/hooks.json` that points at a file **must** use
`${CLAUDE_PLUGIN_ROOT}`. The plugin is installed into a Claude-managed directory,
not the user's checkout, so a repo-relative or absolute path works only on the
machine it was written on.

## Commands

| Command | Does |
|---|---|
| `/ezmodo:start <what>` | context, `resolve_links`, then create the task or epic `in_progress` before anything is edited |
| `/ezmodo:resume <number\|id>` | load by id — never search — read every knowledge item, report what changed, continue from the first incomplete step |
| `/ezmodo:untracked [what]` | `report_untracked_work` with the branch and `git status` prefilled, and the right `origin` |
| `/ezmodo:submit [note]` | steps, knowledge, `link_commit`, clear link suggestions, then `in_review` |

They are deliberately thin — the reasoning lives in the skills, so a rule is
written once rather than in a command and a skill that slowly disagree. Each
costs ~30 tokens always-on and 340-540 when invoked.

`start`, `untracked` and `submit` use `!`backtick`` preexecution to put the real
branch, `git status` and `git rev-parse HEAD` in front of the model, so it never
has to guess at a SHA or a file list.

## Skills

Three, extracted from this repo's `CLAUDE.md` because every repo that uses EzModo
needs the same rules and copying 300 lines of prose into each one guarantees they
drift:

| Skill | Fires when | Covers |
|---|---|---|
| `work-tracking` | starting, resuming or finishing work in a repo with `.ezmodo/config.json` | session init, create-before-you-edit, step toggling, knowledge capture, `report_untracked_work`, context recovery, `link_commit`, completion → `in_review` |
| `link-upkeep` | work touches a component, or a response returns `linkSuggestions` | `resolve_links`, resolving suggestions with reasons, link provenance, derived-beats-asserted, derived navigation, the feature axis |
| `db-schema-snapshot` | a migration is added or changed | finding the `kind:"db_schema"` catalog, patch vs replace, why replace is expensive, snapshotting every namespace |

They resolve project identity at runtime through
`get_current_project_context()` — no org or project id is baked in, so they work
in any tracked repo. Anything that could only be true of the EzModo monorepo
itself (its introspection command, its Go link-retraction helpers) stayed in that
repo's `CLAUDE.md`.

Always-on cost is ~370 tokens for all three; each loads its full body only when
it fires. `claude plugin details ezmodo@ezmodo` prints the current breakdown.

## Hooks

Two rules in the skills are the ones most often forgotten, because asking is all
a skill can do. These notice instead:

| Hook | Fires on | Says |
|---|---|---|
| `link-commit-reminder` | `PostToolUse(Bash)` matching a `git commit` | the full 40-char SHA, branch and subject, plus the active task's id — so `link_commit` needs no guesswork |
| `untracked-edit-reminder` | `PostToolUse(Edit\|Write\|MultiEdit\|NotebookEdit)` | that code was edited with no active task, once per session |

Both cost nothing in model context — they run in the harness and speak only when
they have something to say.

**The commit hook resolves the SHA itself** rather than leaving it to the model.
`link_commit` rejects anything but a full 40-character hash, and a model that has
just watched `[branch 9b5d893]` scroll past will reach for those seven
characters.

**The edit hook reads `.ezmodo/active-session.json`**, which the MCP server
already writes on an `in_progress` transition and clears on completion. Reading
what EzModo actually believes beats a hook keeping state of its own.

### They must degrade quietly

A hook that errors, blocks, or warns when EzModo is unreachable makes the plugin
worse than not having it — and a hook that talks too much gets switched off. So
every path exits 0, and every one of these is silent:

- no `.ezmodo/config.json` anywhere up the tree (not an EzModo repo)
- unparseable or absent hook payload
- a `Bash` call that is not a commit; a commit with no resolvable `HEAD`
- an edit to `.ezmodo/` or `.zephly/` itself, or to a path outside the repo
- an edit while a task **is** active
- the second and every later untracked edit in one session

The once-per-session marker lives in the OS temp directory keyed by session id,
never in the checkout — a hook that leaves a stray file in someone's diff has
already failed.

## The MCP server

`.mcp.json` launches the server from npm at an exact version:

```json
{ "command": "npx", "args": ["-y", "@ezmodo/mcp-server@0.12.9"] }
```

It is **not** bundled in this directory, and it cannot be. Installing a plugin
copies only the plugin's own subtree into `~/.claude/plugins/cache/`, so the
repo-root `mcp-server/` never arrives and a `${CLAUDE_PLUGIN_ROOT}/mcp-server/`
path would point at nothing. The alternatives were committing a second copy of
~30 tool schemas here, or requiring the `ezmodo` CLI as a prerequisite the
plugin cannot install; npm needs neither.

`@ezmodo/mcp-server` is published by `.github/workflows/mcp-server-publish.yml`
when a version bump reaches `main`. That workflow refuses to publish if this
file's pin and the package version disagree — otherwise the plugin would ask npm
for a version that does not exist and every tool call would fail with a 404.

It authenticates with **Trusted Publishing (OIDC)**, so there is no npm token in
the repo to rotate or leak. Two things that are easy to get wrong if you touch
that workflow: it needs `id-token: write`, and it must upgrade npm first —
`setup-node` with node 22 ships npm 10.9.x, which predates OIDC support and fails
with a 403 asking for a token. Re-running a failed run is the reliable retry; a
`workflow_dispatch` only detects the version change while the bump commit is
still the tip of `main`.

### Configuration

| Variable | Required | Meaning |
|---|---|---|
| `EZMODO_API_KEY` | no | Your key from https://ezmodo.com/settings/api-keys. No expiry unless you set one. |
| `EZMODO_API_URL` | no | Override the API base, e.g. `http://localhost:8787/api` against a local stack. |
| `EZMODO_OAUTH_SCOPES` | no | Space-separated scopes to request at sign-in. Defaults to read + write. |

The plugin's server is namespaced `plugin:ezmodo:ezmodo`, so it does not collide
with a server the `ezmodo` CLI installed under the bare name `ezmodo`. It does
mean anyone with both gets two copies of the same ~96 tools — which is what
retiring `ezmodo mcp install --claude-code` (#2597) is for.

Both are passed through with `:-` defaults so an unset variable expands to empty
rather than failing expansion.

**Nothing here is required.** With no variable set, the first tool call returns
a sign-in URL; open it, approve the access, retry. The server holds the OAuth
token from then on and refreshes it itself (#2631).

The credential is resolved per call, in this order:

1. `EZMODO_API_KEY` — an explicit credential beats an implicit one, which is
   what makes CI and headless machines predictable.
2. The OAuth token this server obtained for itself.
3. The credential `ezmodo auth login` stored, if the CLI happens to be present —
   the file on Linux and Windows, the Keychain on macOS.

OAuth ranks above the CLI's key deliberately. Both are implicit, so neither wins
on explicitness; what separates them is that the OAuth grant is one a person saw
and approved on a consent screen naming this connector, while the CLI's key is
borrowed from a different program. `authenticate action:"status"` reports which
is actually in use.

The server no longer exits when it finds no credential. That was right when a
key was the only way in, but sign-in now happens in a browser after startup, so
a server with nothing yet is waiting rather than broken — and the exit would
make the zero-configuration case impossible. It also means the failure that
prompted all this is gone twice over: a missing key used to print a perfectly
clear message to a stderr log nobody opens, and all the user saw in
`claude mcp list` was `CONNECTION_CLOSED` (#2611).

The server's build-time environment defaults to **production**. Every in-repo
caller sets `BUILD_ENV` explicitly, so an unset value means an installed copy
like this one; it used to default to development and silently point a real
user's tools at `http://localhost:8080/api`.

## Versioning

The plugin version tracks the **CLI/MCP-server version**, bumped by
`scripts/bump-version.sh cli <version>` along with `cli/package.json`,
`mcp-server/package.json` and `mcp-server/lib/version.js`.

It gets no independent number because it does not ship independently: the plugin
pins an exact `@ezmodo/mcp-server` version, so "which plugin version am I
running" and "which tool surface am I talking to" have to be the same question.
A separate line would let those two drift while both claiming to be current, and
the first symptom would be `npx` failing on a version npm has never seen.

`bump-version.sh cli` rewrites the pin in `.mcp.json` at the same time, and the
publish workflow verifies the two agree before it pushes to npm.
